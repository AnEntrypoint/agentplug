# AGENTS.md

agentplug is the native wasm host (`agentplug-runner`, `agentplug-host`) that loads the gm plugin and its sibling plugins. Work on `main` only and commit as `lanmower`. Pushing `main` runs `.github/workflows/release.yml`, which bumps the patch version, builds every runner target, and publishes the release that running daemons self-update to.

Code carries no comments. Keep `// SAFETY:` justifications and attributes. Put rationale that structure cannot express in this file, the commit message, or the gm recall store.

## Browser verbs

- `serp`, `browser` and `cdp` resolve their page the same way: a `sessionId=` body line, then a JSON envelope `sessionId`, then the dispatching gm session (`dispatch_origin.rs`, from a JSON `session_id` or `SESSION_ID` -- gm's own accepted spellings -- or else the spool task id), then the guest-resolved id, then `default` only when no gm session is derivable. `DispatchOrigin::page_session` is the single implementation.
- `serp` drives the sideloaded `oxibrowser` plugin (`oxibrowser_driver.rs`). The plugin keys pages by the `page` field of each call and keeps at most 16, evicting the least recently used. `session list`, `session close <id>` and `session reset <id>` map to its `list-pages` and `close-page` verbs. A reply without a `page` field comes from a plugin older than the partition, and the driver flags it with `page_partition_unsupported`.
- A configured steel endpoint (`.gm/browser-config.json` `steel_endpoint` or `GM_STEEL_BROWSER_URL`) takes over `serp` as well as `browser` and `cdp`. This is a user decision: steel overrides all three verbs uniformly. `serp` then runs through `browser::run` with `engine: "steel"`, because oxibrowser's body grammar does not map onto a CDP session.
- `dispatch_origin::note_session_activity`/`session_activity_elapsed` record a cross-verb per-gm-session last-dispatch timestamp on every spool dispatch, not only browser/cdp ones. `browser::reap_idle_sessions` uses it: a session whose `owner_gm_session` has itself had zero dispatch activity of ANY kind for `session_owner_gone_idle_timeout_ms` (default 60 s; an owner unknown to the daemon counts as gone once the daemon has run that long) is reaped on that shorter ceiling instead of waiting out the full `session_idle_timeout_ms` (default 30 min) -- this is the fix for real Chrome processes piling up after a subagent finishes and never calls `session close`. A session with no recorded owner activity, or an owner still dispatching (any verb, not just browser ones), keeps the long ceiling; `session list`'s `owner_last_dispatch_ms` exposes the same signal for inspection.

- `.gm/browser-config.json` keys (all optional; a file that is missing or not valid JSON is read as all defaults; `browser.rs` `BrowserRuntimeConfig` and `browser_engine.rs` `BrowserEngineFileConfig` each read it, so an unknown key is ignored):
  - `headless` (bool, default false): launch Chrome with `--headless=new`.
  - `chrome_cdp_endpoint` (string, also env `GM_CHROME_CDP_ENDPOINT`): dial an already-running Chrome instead of launching one; agentplug never kills it. `steel_endpoint` (also env `GM_STEEL_BROWSER_URL`): dial steel-browser. `engine` (`chrome`|`cdp`|`lightpanda`) and `lightpanda_path` (also env `GM_LIGHTPANDA_PATH`) pick the engine. Precedence: chrome endpoint, steel endpoint, `engine`.
  - `session_idle_timeout_ms` (default 1800000) and `session_owner_gone_idle_timeout_ms` (default 60000): the two idle-reaper ceilings described above.
  - `chrome_ready_deadline_ms` (default 30000): how long a fresh Chrome launch or a dialed endpoint gets to answer `/json/version`. `cdp_poll_timeout_ms` (default 1000) and `cdp_poll_interval_ms` (default 250) tune each readiness probe and the pause between probes.
  - `eval_timeout_grace_ms` (default 6000): added to the dispatch's `timeout=` before the node CDP helper is killed.
  - `chrome_extra_args` (array of strings, default none): appended verbatim to the Chrome command line after every built-in flag. Each entry must be a string that starts with `--` and contains no NUL/CR/LF; an entry that fails is dropped and named in `.gm/browser-chrome-profile-<session>/chrome-launch.log` as `[chrome_extra_args] dropped invalid entry ...`, and the launch proceeds. Anything else in the array (numbers, objects) is dropped the same way rather than voiding the whole file. Entries are not checked against flags agentplug owns (`--remote-debugging-port`, `--user-data-dir`), so overriding those breaks the session.
  - `enable_webgpu` (bool, default false): adds `--enable-unsafe-webgpu` when headed; headless always gets it. `headless_disable_gpu` (bool, default false) is the only way a headless launch gets `--disable-gpu`. `chrome_launch_args` in `browser.rs` is the single builder of the Chrome argv (returns `Err` when a requested `gpu=` adapter cannot be resolved), used by the initial spawn and by the no-sandbox retry.
  - `gpu` (`nvidia`|`amd`|`intel`|`default`, also `session new gpu=<x>`, a `gpu=<x>` first body line, env `GM_BROWSER_GPU`; precedence in that order): `gpu.rs` records the choice in `gpu-choice.txt` in the profile dir and `launch_args` resolves the live adapter LUID (PowerShell: `\GPU Adapter Memory(*)` counter instances intersected with the `HKLM\SOFTWARE\Microsoft\DirectX` `AdapterLuid` values, because registry entries alone keep stale LUIDs from earlier boots) into `--use-angle=d3d11 --use-adapter-luid=<high>,<low>`. Verified empirically on a dual NVIDIA/AMD laptop: `--force_high_performance_gpu`, `--force_low_power_gpu`, `--use-webgpu-power-preference` and `--use-webgpu-adapter` do not move ANGLE or Dawn off adapter 0; the LUID flag moves both WebGL2 and WebGPU, headed and headless. Windows only; other OSes get an error rather than a silent default.
  - Every fresh Chrome launch appends a `gpu` report (`gpu::report` runs `cdp_eval.js` mode `gpu`: browser-level `SystemInfo.getInfo`, then a WebGL2 triangle plus `readPixels`, a WebGPU compute dispatch and a rAF count on a throwaway localhost tab, because `navigator.gpu` needs a secure context). `accelerated` is false on a software renderer, fallback adapter, failed draw/compute, gpu_compositing off, or a `gpu=` vendor mismatch. The body `gpu` re-runs it.
  - Launch args always include `--disable-background-timer-throttling --disable-renderer-backgrounding --disable-backgrounding-occluded-windows --disable-features=CalculateNativeWinOcclusion --disable-ipc-flooding-protection`: measured on a 1500-draw WebGL page, an occluded window fell to 1 fps without them and held 60 with them. Per-dispatch CDP instrumentation is opt-in: only `capture`/`profile`/`trace` enable Runtime/Network and collect debug; the draw-call `getError` wrapper (`capture gl`) is opt-in because it dropped the same page from 60 fps to 5 fps and tripled Chrome CPU when it was attached on every dispatch. `Network.enable` for navigation-failure detection is disabled again after the navigation.
  - `browser` with engine `lightpanda` is served by Chrome (with an `engine_note`) where `lightpanda_native_binary_available()` is false, i.e. Windows.
  - `load_extension` (string, path to an unpacked extension directory): adds `--load-extension` and `--disable-extensions-except`, and `load_extension_after_launch` then also calls CDP `Extensions.loadUnpacked` over the browser websocket right after Chrome is ready. Current stable Chrome ignores `--load-extension` unless the profile already has developer mode on, which a freshly created profile does not, so the CDP call is the reliable path and the flag is kept for Chrome builds that still honour it. It is best-effort: no `node`, a CDP error or an unrecognised reply is logged to `chrome-launch.log` as `[load_extension] ...` and never fails session creation; on success the extension id is written to `chrome.extension-id` in the profile dir.
- Dispatches of one page are serialized. A page is keyed by (project root, session id) and `sessionId=<id>` selects it; without the line the dispatching gm session's own page is used. `browser::run` takes that page's lifecycle lock before it writes any per-dispatch temp file (`agentplug-cdp-{eval,script,result}-{pid}-{session}` names are identical for concurrent dispatches of one session, so taking the lock afterwards let one dispatch overwrite or delete another's script and result files). A dispatch that finds the lock held waits, logs to daemon stderr, and its result carries `queued_behind_same_page_dispatch_ms` and `queue_note`; an uncontended dispatch carries neither. For truly parallel browser work give each worker its own `sessionId=<id>`, which is its own tab in its own Chrome process (`session close <id>` when done). The eval's `timeout=` starts counting after the lock is acquired, so waiting never shortens it, but the whole plugin call still runs under the wasm dispatch deadline (`DISPATCH_CALL_DEADLINE_SECS`, 120s for gm) which counts the wait, so a dispatch queued behind a long one can lose its response to `plugin_call_deadline_exceeded`.

- Chrome process lifetime (`browser.rs`). Only sessions the host launched itself (`owns_process`, engine Chrome or Lightpanda) are ever killed; a Chrome dialed through `chrome_cdp_endpoint` or steel is never touched.
  - `chrome_idle_ttl_seconds` (default 300, 0 or absent means the default): a launched session with no browser dispatch for this long is closed. The effective ceiling is the smallest of this, `session_idle_timeout_ms` and (owner gone) `session_owner_gone_idle_timeout_ms`. Idle is measured from the END of the last dispatch (`touch_last_used`). A session whose lifecycle lock is held (a dispatch in flight) is never reaped.
  - The reaper runs on its own thread (`ensure_idle_reaper_running`, started by the first browser dispatch in the process, tick `IDLE_REAPER_TICK` = 15s) over every project that has a tracked session, loading each project's own config, so an idle daemon still reaps. Before this the only callers were the daemon main loop (every 5 minutes, and only between dispatch batches) and the top of the next browser dispatch on the same project.
  - `chrome_max_concurrent` (default 2): cap on launched Chrome processes across every project in this process. The effective cap is the larger of the dispatching project's value and the highest value any project has shown this process (`CHROME_CAP_HIGH_WATER`), so one project cannot lower another's limit. At the cap `reserve_chrome_launch_slot` first reaps idle sessions everywhere, then evicts the least recently used session idle for at least `LRU_EVICTION_IDLE_FLOOR` (60s) that has no dispatch in flight, and otherwise refuses with an error listing every live Chrome (pid, project, session, idle seconds). Launches still in progress count toward the cap (`PENDING_CHROME_LAUNCHES`).
  - `session close-all` closes every session (tracked or adoptable via the `chrome.owner-gm-session` sidecar) owned by the calling gm session; `session close` with no id closes the caller's implicit page; `session close <id>` is unchanged. Each close runs `kill_pid` (`taskkill /F /T`) and then `kill_chrome_processes_left_on_profile`, which kills any chrome whose `--user-data-dir` is that profile (crashpad/GPU children detached from the tree), and removes the pid/port/session-id/owner/last-used sidecars; the profile directory itself stays so cookies persist. Reapers collect victims under the session-map lock and kill after releasing it.
  - `reap_globally_orphaned_gm_chromes` (every reap pass, headed or headless) kills a root chrome with `--remote-debugging-port` and a `.gm/browser-chrome-profile-*` `--user-data-dir` that no session in this process tracks, whose profile sidecars are older than 15 s, and whose parent process is dead (or is this process). The parent check is what stops a second daemon with another `AGENTPLUG_HOME` from killing the first daemon's live chromes; never run a scratch daemon without it.
  - The default page id is the gm session id, so two subagents that share one `SESSION_ID` share a Chrome. Distinct ids come from the caller: `<parent>-sub<k>` for spool verbs, one shared `sessionId=` for a task's browser.
  - `session list` reports per session `pid`, `project`, `idle_seconds`, `owns_process` and `working_set_mb` (the whole process tree: Toolhelp snapshot plus `K32GetProcessMemoryInfo` on Windows, `/proc/<pid>/statm` on Linux, null elsewhere; `process_tree.rs`), and at top level `chrome_process_count` (all projects), `chrome_max_concurrent`, `chrome_idle_ttl_seconds` and `chrome_sessions_all_projects`.
  - Tree kill: Windows `kill_pid` is `taskkill /PID <pid> /F /T`. On Unix it used to be `kill -9 <root>` only; Chrome is now spawned in its own process group (`process_group(0)`) and `kill_pid` signals the group first. A Chrome adopted from an older daemon is not a group leader, so only its root is signalled and its children exit with it. `session close <id>` now also adopts and closes a Chrome that survived a daemon recycle but is not yet in the session map.
  - Why sessions used to survive: every daemon self-update handoff calls `close_all_sessions`, which deliberately detaches Chrome so the successor can adopt it, and adoption stamped `last_used` with the adoption time, so a recycle restarted the 30 minute clock and the in-memory owner-activity map (used for the shorter owner-gone ceiling) starts empty in the successor. With releases landing faster than 30 minutes apart an adopted Chrome was never idle long enough. Adoption now derives `last_used` from the newest of the `chrome.last-used`, `chrome.target-id` and `chrome.pid` sidecar mtimes. Handoff still detaches on purpose (it keeps page state across an update); the successor's reaper then enforces the TTL.

## Runner self-update and plugin install (`download.rs`)

- GitHub's plain `/releases/latest/download/{asset}` redirect resolves through `objects.githubusercontent.com` with `/releases/download/{tag}/` in the path, so the tag is extractable from the resolved URL without touching the rate-limited, sometimes proxy-scoped `api.github.com`. A newer redirect shape (seen live for `agentplug-bert-bin`) instead goes through `release-assets.githubusercontent.com` with an opaque object id and a presigned query string -- no tag segment anywhere, only the asset filename in the `rscd` query param -- so `extract_version_from_release_url` cannot parse it; `resolve_latest_tag_via_release_page` falls back to `https://github.com/{repo}/releases/latest`'s own redirect target (`/releases/tag/{tag}`), which is a separate, stable contract unaffected by either failure mode.
- `api.github.com` can 403 (60/hr unauthenticated, 5000/hr with `GITHUB_TOKEN`/`GH_TOKEN`) or be blocked/proxy-scoped independently of the plain releases-download redirect; both runner-version and plugin-version resolution fall back to the redirect path (`try_ensure_plugin_installed_via_direct_release_latest`, `fetch_latest_runner_version`'s fallback leg) instead of stalling the self-update/install check for the rest of the process's life.
- A repo shared by more than one plugin family (`AnEntrypoint/plugkit-bin` publishes both `gm` and rs-codeinsight's own releases) means `/releases/latest` can return a sibling family's release with no `plugkit-slim`/`plugkit` asset at all; `fetch_latest_plugin_version` scans up to 100 recent releases (GitHub's page max -- live-witnessed a target release ~21 positions deep behind a high-cadence sibling) for the newest one that actually carries this plugin's asset.
- `download_and_verify`'s tmp file is `<dest>.tmp.<pid>`. A failed rename (Windows `ERROR_SHARING_VIOLATION` when `dest` is locked/mapped by a running process -- the normal case for self-update staging and plugin hot-swap) leaves the sha256-verified tmp file in place rather than deleting it, so a caller retrying the rename does not have to re-download. `gc_stale_tmp_files` sweeps both real leak sites (`install_dir()/plugins` and the running exe's own directory) at daemon startup, bounded by file age rather than pid liveness since a pid can be reused by an unrelated process. Known gap: the exe-dir sweep only knows this run's own `current_exe()` directory, so a leaked tmp file from a since-relocated install location is never found.
- A process running from its own `.new`-staged path (`stage_runner_self_update`) must stage the next update under `.new2`, not `.new` again: Windows keeps a running process's own loaded image file locked, so writing the next stage to that same path collides with itself forever.
- `promote_staged_exe_to_canonical` (`daemon.rs`) refuses to promote onto a canonical path that is a cargo build output (a `target/` dir beside a `Cargo.toml`) -- a daemon started straight from `cargo build`'s own `target/release` tree must never self-update onto that path, since doing so would overwrite the build artifact out from under the workspace that produced it.
- `snapshot_prev_wasm_and_version` always pairs a `.wasm.prev` backup with a `.version.prev` backup before an install overwrites either, and `record_plugin_load_failure_and_rollback` always restores both together: restoring only the wasm bytes while leaving `.version` pointing at the new, failed release tag would make `refresh_plugin_if_stale` believe the rolled-back (older) binary on disk is already current and stop checking for updates entirely.
- A plugin release can outpace this runner's own release cadence (a plugin repo ships a release built against a newer host-import contract, e.g. a changed `host_browser_exec`/`host_fs_cas_write` signature, before `agentplug-bin` has a matching update) and fail to instantiate. `record_plugin_load_failure_and_rollback` restores the last version that DID load and records the failed tag via `record_known_bad_version` so `refresh_plugin_if_stale` does not immediately re-fetch and re-fail the same tag on its next poll tick; the blacklist is cleared on every runner self-update (`clear_all_known_bad_version_markers`) so a previously-incompatible version gets a fresh chance against the new host ABI.
- `get_or_compile` calls `ensure_plugin_installed` on every daemon main-loop tick (100ms) for every configured plugin. `PLUGIN_INSTALL_RETRY_COOLDOWN` (30s) exists because an ungated retry at that rate exhausts GitHub's unauthenticated 60/hr rate limit in under two seconds and keeps it exhausted; the cooldown timestamp is a file next to the plugin's own wasm/version (not an in-process clock), because a self-update handoff or a one-shot CLI `plugin`/`dispatch` invocation is a separate OS process that would otherwise have no memory of a still-live backoff.
- `.agentplug/plugins.json` (a project-declared `{name, repo, asset_basename}` array) names where to DOWNLOAD an extra or overridden plugin from; the sibling `.agentplug/plugins.txt` only names which plugins to LOAD. A project's own declared spec wins over the compiled-in built-ins for any plugin name, including the 4 built-in ones. A one-shot CLI `plugin`/`dispatch` invocation never sees the daemon's own known-roots registry, so `plugin_asset_spec` also always checks the invoking process's own cwd.

## Spool dispatch concurrency (`daemon.rs` `dispatch_project`, `registry.rs`)

- `dispatch_project` claims every settled in-file of the project on each tick, oldest mtime first, up to `MAX_CLAIMED_DISPATCHES_PER_PROJECT` (32) minus what is already in flight, and spawns one named thread per claim without waiting for it. The thread owns its `in_flight_map` entry through `InFlightEntryRelease`, so a panic still clears it. The claim key stays `(verb, <session_id>-<N>)` and the in-file is still claimed by rename; the orphan sweep is untouched.
- There is no project-level gate on in-flight work. The pre-fix gate (`project_has_in_flight_step` at the top of `dispatch_project`, added in 3970f79 together with `PROJECT_BATCH_ABSORB_WINDOW_MS = 0`) held every later in-file of a project unclaimed until the slowest in-flight dispatch finished, and after the 45 s auto-detach it made the main loop spin at about 85% of a core because in-flight work counted as pending work. `project_has_pending_dispatch_work` now counts only claimable in-files.
- `GmFairnessGuard::acquire(root, verb, body)` serialises per `(project, lane)`. `UNSERIALIZED_VERBS` (exec family, `serp`/`browser`/`cdp`, `fetch`, read-only `fs_*`/`git_*`/`prd-*`/`mutable-*`, `phase-status`, `status`, `wait`, `close`, `filter`) and a `codesearch` in any mode but `dual` take no lane and skip `ToolDispatchGuard`; browser pages are keyed per gm session, so they need no lock. Everything else takes the `git`, `store` (memory, recall, index, sql, cache, kv writes, dual `codesearch`) or `state` lane, default `state`, so state-file writers of one project still run one at a time while a slow `recall` or `git_finalize` cannot hold a `prd-add`. A new verb is serialised until it is added to `UNSERIALIZED_VERBS`. A dispatch thread that cannot be spawned is answered with an error out-file at once instead of leaving its claim for the ten-minute orphan sweep.
- `dispatch_origin.rs` exposes `AGENTPLUG_DISPATCH_SUBMITTED_AT_MS` (the in-file's mtime) and `AGENTPLUG_DISPATCH_TASK` to the guest through `host_env_get`, read from the current dispatch scope, never from the process environment. `queue_wait_ms` is measured from the in-file's mtime, not from the claim.
- The `gm` pool defaults to 8 slots (`DEFAULT_GM_POOL_SIZE`, capped by host parallelism and `MAX_GM_POOL_SIZE`, `gm_pool_size` in `daemon-config.json` overrides; lower it to restore the earlier 4). A dispatch holds one slot for its whole run, including a long `exec_js`, so the pool size is the remaining bound on how many slow dispatches can run before a quick one waits. Heavy verbs stay capped at `MAX_CONCURRENT_HEAVY_DISPATCHES` (3) slots.
- Measured on a scratch daemon (`AGENTPLUG_HOME` pointed at a scratch dir, a separate project root, `GITHUB_TOKEN` set to a dummy so no update or credential path is live): one 30 s `exec_js` plus eight quick dispatches claimed in 13-31 ms and finished in 63-343 ms; the same run before the change claimed the quick ones after 29.7-30.4 s. The gm plugin denies `exec_js` with `long-gap-no-instruction` once the last `instruction` dispatch is more than 300 s old, so prime a scratch project with `instruction` before timing anything.

## Windows release checkout

The Windows jobs of `release.yml` fail at `actions/checkout` with `Filename too long` when any tracked path is longer than about 230 characters, and a failed Windows build skips `publish`, so no runner is released and running daemons never update. `.agentplug-kv/git_commit_dedup/` holds one file per commit named after its message and paths; it is ignored, not tracked. Keep every tracked path short.
